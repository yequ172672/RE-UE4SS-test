# UE4SS AI MCP 产品需求文档

> 状态：需求基线草案
>
> 日期：2026-08-14
>
> 当前口径：优先满足本地开发与调试，公开发布前另行完成安全审计

## 1. 产品定义

UE4SS AI MCP 是面向实际游戏、UE4SS 和模组开发工具的 AI 操作接口。它让 AI 不只读取源码或回答问题，而是能够直接完成游戏识别、模组创建、构建、安装、运行、调试、修改和验证。

“完整操作”在本文中表示：凡 UE4SS、目标游戏、编辑器、编译工具链或调试器已经能够完成的操作，都应尽可能转化为 AI 可发现、可组合、可验证的能力。系统不以少量预设工作流限制 AI，也不要求每个新游戏先获得全局版本认证。

## 2. 当前问题

UE4SS 已经提供 Lua、蓝图、C++ 模组、反射对象、Hook、控制台、日志和调试相关能力，但 AI 尚不能稳定地把这些能力串成实际闭环：

- 不清楚当前连接的是哪个游戏、哪次运行以及有哪些真实可用能力。
- 模组源码生成、构建、安装、加载、调试和结果验证彼此割裂。
- AI 很难可靠处理对象生命周期、地图切换、游戏线程和运行时类型。
- 蓝图产物依赖目标 UE 版本、编辑器资源和打包条件，仅生成文件不等于可运行。
- C++ 模组依赖正确的 UE4SS 接口、工具链和二进制兼容条件。
- 日志和命令输出多为面向人工的文本，AI 难以判断“已请求”“已加载”和“行为正确”的差别。
- 现有能力缺少统一的结构化错误、状态快照和可重复验证方式。

## 3. 产品目标

产品必须让 AI 能完成以下闭环：

1. 发现或启动目标游戏，识别 UE4SS、游戏版本、运行状态和可用能力。
2. 读取模组、日志、对象、类、函数、属性、线程和调试上下文。
3. 创建或修改 Lua、蓝图和 C++ 模组。
4. 调用所需编辑器、构建工具和打包能力，生成真实可运行的产物。
5. 安装、启用、禁用、加载、重载或移除模组。
6. 操作游戏运行时，执行脚本、函数、控制台命令、Hook 和对象读写。
7. 调试 Lua、Kismet/蓝图和 C++，读取断点、调用栈、变量、异常与崩溃信息。
8. 根据运行证据修改模组或操作步骤，并自动复验。
9. 把一次成功调试沉淀为可重复执行的场景和断言。

## 4. 范围说明

### 4.1 包含范围

- 实际运行中的 UE4SS 游戏会话。
- UE4SS 自带及可扩展的 Lua、蓝图和 C++ 模组能力。
- 目标游戏所需的 Unreal Editor、打包工具、编译工具链和调试器能力。
- 模组工作区、游戏模组目录、配置、日志、符号、构建产物和调试产物。
- 游戏对象反射、低层内存、函数调用、Hook、事件、控制台与线程相关操作。
- 面向 MCP 客户端的工具、资源、状态和事件。

### 4.2 不包含范围

- 不把 UE4SS 源码仓库本身当作最终操作对象；源码只作为能力定义和行为参考。
- 不承诺从运行时对象完整还原未公开的蓝图源图或 C++ 源码。
- 不承诺在缺少匹配编辑器、SDK、符号或工具链时生成等价产物。
- 不开发反作弊绕过、隐藏注入或面向联网对局的作弊功能。
- 不承诺所有游戏和所有版本拥有相同能力；兼容性按具体能力报告。
- 本文不规定公开发布版本的最终权限策略，该部分由发布前安全审计决定。

## 5. 使用模式

### 5.1 开发模式

开发模式服务于本地研究、模组开发和游戏调试。用户明确选择目标进程与开发目录并启用开发模式后，AI 应获得当前环境能够提供的完整能力，不再对每个写入、函数调用、脚本执行、Hook 或调试动作逐项询问。

开发模式要求：

- 不默认只读，不按固定能力等级锁住 AI。
- 允许连续调用多个工具完成长链路任务。
- 允许任意 Lua 代码执行、反射函数调用、控制台命令和运行时对象修改。
- 允许在环境支持时进行地址查询、内存读取、内存写入、对象创建/销毁和 Hook 管理。
- 允许启动、附加、暂停、继续、重启或停止目标游戏与相关开发工具。
- 允许读写用户为本次开发指定的工作区、游戏目录、编辑器工程、构建目录和调试产物目录。
- 允许 AI 自主重试、修改产物和重复验证，直到达到用户给定断言或明确报告阻塞。
- 对危险动作可以提示影响，但提示不能变成逐项人工审批流程。

开发模式仍需保留对象有效性检查、错误返回、超时、取消、执行记录和结果读回。这些要求用于避免 AI 因错误状态误判任务完成，不用于限制其能力范围。

### 5.2 发布模式

发布模式面向未来对外分发的产品。其身份认证、远程访问、目录范围、高风险工具开关、用户确认、隐私、审计和反作弊环境策略，在正式发布前通过专项安全审计确定。

当前需求只要求所有能力能够被独立识别和标记，以便安全审计可以按工具关闭、限制或增加确认，而不需要重做产品能力定义。开发模式不得因为尚未完成发布策略而被提前削弱。

| MCP-001 | MCP 客户端必须能够发现会话、模组、Lua、蓝图、C++、运行时、调试、文件与验证相关能力。 |
| MCP-002 | 每项工具必须说明用途、输入、输出、副作用、前置条件和常见失败原因。 |
| MCP-003 | 大型日志、对象集合、类型定义、状态快照和产物清单应能作为可分页资源读取。 |
| MCP-004 | 日志、断点、地图切换、对象失效、模组加载和构建状态应能以事件形式持续提供。 |
| MCP-005 | 能力不可用时必须返回缺少的游戏状态、依赖或工具条件，而不是只返回“不支持”。 |
| MCP-006 | 一个客户端断连不得导致游戏永久暂停、任务状态永久占用或后续客户端无法接管。 |
| MCP-007 | 工具结果必须区分请求已接受、正在执行、已产生结果、已验证和需要重启。 |
| MCP-008 | AI 必须能够取消长任务，并在取消后读取已经发生的实际变化。 |

## 7. 会话与能力发现需求

| 编号 | 需求 |
| --- | --- |
| SES-001 | 系统必须发现可连接的本地游戏进程，并返回进程、游戏、版本与 UE4SS 候选信息。 |
| SES-002 | 系统必须支持启动游戏、附加到运行中游戏、重新连接、重启和停止游戏。 |
| SES-003 | 每次连接必须具有唯一会话标识，并返回当前 World、地图、线程和模组运行摘要。 |
| SES-004 | 进程退出、重新启动或目标切换后，旧会话必须明确失效。 |
| SES-005 | 地图与 World 切换必须可观察，相关旧对象句柄必须被标记失效。 |
| CAP-001 | 系统必须返回当前现场验证得到的能力清单，不要求 AI 根据版本号猜测。 |
| CAP-002 | 能力状态至少区分 `available`、`degraded` 和 `unavailable`，并说明依据与缺失部分。 |
| CAP-003 | 单项能力因结构变化不可用时，其他不依赖该结构的能力应继续工作。 |
| CAP-004 | 未知游戏版本不构成全局拒绝理由；系统应尽可能探测并开放能够验证的能力。 |
| CAP-005 | AI 必须能够刷新能力状态，以处理游戏初始化、地图切换和工具启动后的变化。 |

## 10. 蓝图模组需求

蓝图创作与运行时操作是两项独立能力。运行中的游戏可以提供类、对象、函数和 Kismet 状态，但生成可编辑、可编译和可打包的蓝图仍取决于匹配的 Unreal Editor 与目标资源条件。

| 编号 | 需求 |
| --- | --- |
| BP-001 | AI 必须能够创建或打开目标编辑器工程，并识别目标游戏所需的 UE 版本、插件与资源条件。 |
| BP-002 | AI 必须能够用结构化方式创建蓝图类、选择父类、添加变量/函数/事件并编辑节点连接。 |
| BP-003 | AI 必须能够读取蓝图结构、编译诊断、节点位置、变量默认值和引用关系。 |
| BP-004 | AI 必须能够保存、编译、修复、Cook、打包并校验蓝图模组产物。 |
| BP-005 | 系统必须支持目标游戏实际采用且已能验证的 Pak 或 IoStore 产物。 |
| BP-006 | AI 必须能够安装完整蓝图模组产物，并确认游戏是否挂载、类是否加载和实例是否创建。 |
| BP-007 | 系统必须支持发现和操作 `ModActor_C`，并调用目标约定的生命周期与模组菜单入口。 |
| BP-008 | AI 必须能够读取和修改蓝图实例公开状态、调用蓝图函数并观察执行结果。 |
| BP-009 | Kismet 调试可用时，AI 必须能够设置断点、继续、暂停、单步、读取节点位置、调用栈与变量。 |
| BP-010 | 蓝图更新后，系统必须尝试环境实际支持的重载方式；如只能重启生效，应准确返回该状态。 |
| BP-011 | 缺少编辑器或资源条件时，系统仍应保留对现有蓝图对象的运行时查询、调用和调试能力。 |

## 16. 统一结果与错误需求

每次操作至少返回：

- 操作标识、会话标识和目标。
- 状态：`succeeded`、`failed`、`partial`、`indeterminate`、`cancelled` 或 `rejected`。
- 实际执行内容、产生的变化和当前状态。
- 关键日志、读回值、文件校验或其他验证证据。
- 是否需要重载、重启或重新连接。
- 结构化错误及可继续尝试的动作。

错误至少包含稳定错误码、发生环节、简明消息、结构化上下文和是否适合重试。基础错误类别包括：

| 错误码 | 含义 |
| --- | --- |
| `transport.protocol_mismatch` | MCP 客户端与当前服务能力不兼容。 |
| `lifecycle.runtime_not_ready` | 游戏或 UE4SS 尚未进入所需状态。 |
| `capability.unavailable` | 当前现场无法提供所需能力。 |
| `capability.structure_changed` | 所需结构与预期不一致。 |
| `object.expired` | 对象因 GC、销毁、地图或会话变化而失效。 |
| `thread.unavailable` | 所需线程上下文不可用。 |
| `operation.timeout` | 操作未在限定时间内完成。 |
| `operation.indeterminate` | 连接中断后无法确认操作是否产生副作用。 |
| `mod.abi_mismatch` | C++ 模组与目标二进制条件不匹配。 |
| `mod.build_failed` | 模组构建失败。 |
| `mod.restart_required` | 变化已准备完成，但重启后才生效。 |
| `editor.profile_unavailable` | 缺少匹配的蓝图编辑或打包条件。 |
| `editor.cook_failed` | 蓝图资源 Cook 或打包失败。 |
| `debug.target_resumed` | 调试连接异常后目标已恢复执行。 |

非幂等操作在断连后不能确认结果时，必须返回 `indeterminate`，避免 AI 因误判而重复执行。

## 17. 非功能需求

### 17.1 可靠性

- 工具必须校验对象是否仍存在、类型是否匹配以及目标线程是否可用。
- AI 必须能取消长操作，并读取取消前已经发生的实际变化。
- 日志、对象扫描和事件流必须有分页、进度或背压信息，不能让结果无限增长。
- 客户端断连不得让游戏永久停在断点或等待状态。

### 17.2 兼容性

- 兼容性按具体能力声明，不采用简单的全局版本白名单。
- 目标配置必须区分游戏版本、UE 版本、UE4SS 构建、模组类型与打包条件。
- 遇到结构变化时，只拒绝依赖该结构的能力，并允许 AI 继续探索其他能力。
- 所有兼容性结论必须能指出现场证据或实际失败点。

### 17.3 可观察性

- AI 能查询正在执行、已完成、已取消和失败的任务。
- 长任务必须提供进度、当前动作和近期输出。
- 对游戏产生的写入、调用、Hook、输入和文件变化必须保留本次开发会话的操作记录。
- 操作记录服务于调试和复现，不在当前需求中引入逐项审批。

### 17.4 性能

- 常规状态查询不能持续造成用户可感知的游戏卡顿。
- 大型扫描和高频观察必须允许 AI 调整范围、频率和返回量。
- 明确的暂停、断点和单步操作可以阻塞目标线程，但暂停状态必须可见并可恢复。

## 18. 验收场景

### 18.1 通用会话

- AI 能发现或启动一个本地 UE4SS 游戏，连接后读取实际能力清单。
- AI 能查看已加载模组、当前地图、日志和可查询对象。
- 地图切换后旧对象句柄失效，AI 能重新发现新对象继续工作。
- 一项结构探测失败时，其他不相关能力仍能继续使用。

### 18.2 Lua 闭环

给定一个自然语言模组需求，AI 能：

1. 创建并安装 Lua 模组。
2. 启动模组并确认入口真实执行。
3. 通过任意 Lua 求值探索对象与 API。
4. 捕获一个故意错误的文件、行号和调用栈。
5. 设置断点，读取局部变量并继续执行。
6. 修改脚本、重载模组并通过日志和对象状态复验。
7. 移除模组并确认运行状态。

### 18.3 蓝图闭环

给定 `HelloMcp` 模组需求：

- 资源路径为 `/Game/Mods/HelloMcp/ModActor`，运行类为 `ModActor_C`。
- 公开整数属性 `Counter` 初始为 `0`。
- 提供 `PreBeginPlay`、`PostBeginPlay` 和 `ModMenuButtonPressed` 行为。
- 第 0 个菜单按钮被调用后，`Counter` 从 `0` 变为 `1`。

AI 必须能够：

1. 确认目标编辑器和资源条件。
2. 创建蓝图、编译、Cook、打包并安装完整产物。
3. 确认游戏挂载产物、加载类并创建预期实例。
4. 调用生命周期和菜单入口，读回 `Counter == 1`。
5. 在可用时对 Kismet 设置断点并读取执行上下文。
6. 地图切换后识别旧实例失效并重新获取实例。
7. 修改蓝图后用环境实际支持的方式重新生效并复验。

如果缺少匹配编辑器条件，AI 必须准确报告缺少项；现有蓝图对象的运行时操作仍可继续。

### 18.4 C++ 闭环

AI 必须能够：

1. 创建一个与目标 UE4SS 条件匹配的 C++ 模组。
2. 构建并根据结构化诊断自动修复编译错误。
3. 安装产物并确认加载、入口执行和指定行为。
4. 注册一个 Hook，观察其命中，再注销 Hook。
5. 附加原生调试器、命中断点并读取调用栈与变量。
6. 修改源码后重新构建，并通过重载或重启让修改生效。
7. 在故意异常场景中获取日志、异常和可用崩溃产物。

### 18.5 运行时探索与修改

AI 必须能够：

1. 查询玩家类和当前实例。
2. 读取并修改一个属性，再读回实际结果。
3. 调用一个带参数的反射函数并读取返回值。
4. 注册函数 Hook、观察命中参数并移除 Hook。
5. 执行一条控制台命令并观察游戏变化。
6. 在开发模式下读取指定内存、修改测试值并读回。
7. 地图切换后停止使用旧对象并在新 World 继续任务。

### 18.6 自动调试任务

给定一个存在逻辑错误的模组，AI 能自主完成：复现问题、采集证据、定位代码或节点、修改、重新生效、重放场景和验证断言。最终结果必须包含实际改动、执行证据、仍存在的问题和无法验证的部分。

## 19. 发布前安全审计门槛

当前开发版本不因未来发布策略限制 AI 能力。任何面向非开发者或允许远程访问的正式版本，在发布前必须单独完成安全审计并形成发布结论。

安全审计至少评估以下对象，但限制方式由审计结论决定：

- MCP 的身份认证、连接范围与远程暴露面。
- 任意脚本、内存读写、原生调用、Hook、调试器和进程控制能力。
- 游戏目录、用户文件、工具链和凭据的访问范围。
- 反作弊环境、联网游戏和第三方平台规则。
- 日志、转储、源码、路径和游戏数据的隐私处理。
- 提示注入、恶意模组输出、路径穿越和资源耗尽风险。
- 默认开关、风险提示、用户确认、操作记录和紧急停止能力。

未完成安全审计的版本可以作为本地开发工具使用，但不得标记为已达到公开发布安全标准。

## 20. 完成定义

一个能力只有同时满足以下条件，才可在开发模式中声明可用：

- AI 能从 MCP 发现它，并理解输入、输出与副作用。
- 能在实际游戏或实际工具中执行，而不是只生成计划或示例代码。
- 能返回真实状态、结构化错误和可核验证据。
- 能处理对象失效、地图切换、工具未就绪、超时和断连。
- 能与其他工具组合成模组创建、运行、调试和复验闭环。
- 有至少一个正常场景和一个失败场景的可重复验收记录。

产品整体完成必须分别通过 Lua、蓝图、C++、运行时操作和自动调试任务的验收场景。公开发布完成还必须额外通过第 19 节的安全审计门槛。

## 21. 待确认的产品决策

- 首批用于完整验收的目标游戏与游戏版本。
- 首批正式支持的蓝图产物格式和匹配编辑器范围。
- 原生调试需要覆盖的调试器与符号来源。
- 游戏窗口自动操作需要覆盖的输入和画面验证范围。
- 是否需要把成功的调试场景导出为可共享测试包。
- 开发模式的操作记录、日志与崩溃产物默认保留期限。
