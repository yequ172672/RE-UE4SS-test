# Phantom Blade Zero compatibility data

This configuration was tested with the Steam executable SHA-256 `7b4fcd286a350780faf0824d73aa150b21cbf1bccde883e6a96386cbe09973b4` and UE 5.7. Offsets and signatures are build-specific and must be revalidated after a game update. The executable and project selectors are based on this installation's executable directory structure.

The configuration permits UE4SS initialization, C++ header and USMAP export. With the `-basedir` directory discovery change, the blueprint mod loader initializes and finds the project content directory; loading an actual blueprint mod has not been verified. GNatives points to the bytecode dispatch table. The hash-table getter candidate is used by the game's HashOuter path. The current UE4SS Lua scan callback logs its address but does not assign it to a runtime consumer; the override also prevents the mandatory patternsleuth scan from requesting that resolver. Do not interpret the scan log as proof of an active hash-table integration. Generated headers describe objects loaded during the dump and are not a complete or independently validated SDK.

The current layout was checked against live `Actor`, `Function`, and `AssetData` objects: class flags and cast flags are at `0x124`/`0x128`, while `AssetData` has size `0x68` and struct flags `0x1003` at `0x100`. A fresh USMAP was independently parsed and its extension flags checked: Actor `0x30c800a4`, AssetData `0x1003`. It contains 72,387 names, 2,985 enums, 15,510 structs and 59,483 properties in the tested session. These counts depend on loaded objects.

The `UClass::Interfaces` offset `0x230` is supported by read-only inspection of nonempty interface arrays across the running game. An inherited `SetHiddenInGame` call also succeeded after restarting with this layout.

The FName signature selects the wide-character overload accepting EFindName. The previously tested overload interpreted that argument as a numeric suffix and produced names such as `pelvis_0`; the replacement returned `pelvis` and `pelvis_2` correctly in the running game.

The later Lua FName argument and UTF-8/ANSI property-handler changes have been built and tested in isolated harnesses, but were not installed into the running game for validation. Build the current source before testing those changes; the generated SDK and USMAP are not included in the repository.

In a prior running session, Lua `LoadAsset` reported a known asset as not found while the Kismet soft-object-path loading route loaded it. That test used the old FName constructor. After the corrected signature was loaded, a game-thread test of the MuXiaoKui body asset returned `found=true` and `loaded=true`; this validates that asset path in the current session but does not establish general asset-loader correctness. The registry's reflected `GetAssetByObjectPath` function is present in this game and its return value is at offset `0x10` with size `0x68`. The `FAssetData` array iterator uses the reflected runtime size, so a wrapper-size mismatch alone does not establish an array iteration error. Do not assume that the unreflected members or copy operations are correct without further validation.

The C++ header dump completed with 3,876 files in the tested session, but the generator logged seven enum properties whose enum value was invalid. Those properties were omitted; investigate them before relying on the dump as a complete SDK.

All seven reported properties are comparison-method enums on SGameAI blueprint classes; other enum properties are present in the dump, so a global enum-layout fault has not been established. The affected classes were absent from the preceding USMAP snapshot, so those two exports cannot be compared as if they captured the same loaded objects. `ProcessConsoleExec` was resolved from the UObject vtable to `0x1414ba510`, but its hook failed to install. In this executable the resolved function is a 19-byte wrapper around a call to `0x14162f640`. A separate-process PolyHook test successfully hooked a wrapper with the same instructions after hooking its callee, so the short wrapper alone does not explain the failure. Forcing the larger in-place detour scheme made the same wrapper fail with `Function too small to hook safely`; the short in-place scheme succeeded. An isolated calling-convention test of the short scheme preserved the four incoming arguments, the wrapper's fifth stack argument, and the return value through hook and unhook. The callee's live patched bytes indicate that an in-place detour was used there, making detour scheme selection a plausible cause for the wrapper failure, but the wrapper's failed attempt has not been instrumented. Further diagnostics require a controlled restart before changing the implementation or vtable layout.
